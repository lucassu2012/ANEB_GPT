## 一页操作顺序

1. **先确认可执行**：只使用现场可直接使用的 Kimi 手机 App。记录实际可见版本、模型/模式；不可见填 `UNKNOWN`，不要用网页说明代替手机事实。若需索取/创建账号、无法新建会话、无法原样发送任务或无可判读录屏条件，记 `NOT_RUN`，不换 App 或账号补齐。
2. **固定观察口径**：R1 前写明一种 `SEND_anchor`（发送已生效的可见锚点）、一种 TTFR 反馈类型、最终正文 `BODY_region` 和录屏时间基准，三次不变。用户文字、思考/推理、搜索/工具、加载提示和按钮文字不算最终正文。
3. **固定条件**：只做 C0，即现场既有且未人为改变的网络。无 shaping、VPN、隧道、抓包或 C1/C2。只登记可观察事实，不为得到结果改变模型、UI、任务或网络。
4. **发送固定任务**：每次新建空白会话，发送下文原文，不追问、不修改、不因回答质量补跑。
5. **顺序固定**：`C0-R1 → C0-R2 → C0-R3`。每次保留原始记录，包括失败、取消、观察缺口和未运行；不追加第四次凑有效结果。条件无法保持时停止受影响运行；整个执行前提失效时停止整组。
6. **独立标注**：A、B 分别观看同一原始视频，先提交各自原始表，再比较。分歧另写协调记录，不覆盖 A/B 值。不确定就保留区间、`NA` 或 `uncertain`。
7. **结束与保管**：R3 后结束，不追加另一 App 或网络条件。按参与方约定保存原始视频、标注与结果卡；不自动上传或对外分享。若使用 P40，执行前后仍遵守仓库 AGENTS 的实时清场要求，不停止未知会话。

### 固定任务：每次逐字相同

```text
请只用中文回答：用恰好10个编号要点解释“为什么移动网络时延会影响AI助手的交互体验”。每个要点写2句话；不要使用表格，不要调用外部工具，不要向我提问。
```

## 事件、停止与完成

所有边界都来自同一原始视频的可见帧，记录帧号或最小可判读帧区间。正文更新只指最终正文的新增或改写，纯滚动/动画不是更新。

| 记录项 | 操作定义 |
|---|---|
| T0 | 预定 SEND_anchor 首次可见成立。实际未发送才记 `NOT_RUN`；已发送但无法确定 T0，保留已执行状态，T0 及依赖它的时长填 `NA` 并记录原因，不猜起点或倒改为未运行。 |
| TTFR | T0 到预定反馈类型首次可见；记录反馈类型及事件帧，不能事后挑更早的另一类型。 |
| TTFC | T0 到 BODY_region 首次出现任务相关助手最终正文；不算思考/状态/工具/用户文字。 |
| 完整可见停顿 | 两次相邻正文更新之间全程可观察、且随后确实恢复更新的完整间隔。起点是前次更新、终点是首次恢复；完整时长达到 2.0 s 才计，不是满 2 s 后才开始计。 |
| 尾段与观察缺口 | 最终正文后的终止静默不计停顿；未恢复的尾段记 `right_censored / unclosed`，不能计完整停顿或精确最长停顿。滚动、遮挡、正文出屏、画面不可判读记 `observation_gap`，不得跨缺口拼接已确认停顿。 |
| T3 | 最后一次可见正文更新的候选边界。之后须连续至少 3.0 s 正文与相关 UI 均可判读、无进一步正文更新，且 UI 可见已退出生成、不是错误/取消/异常终止，才确认。窗口内再次更新就换用新的最后更新候选。T3 是最后更新时刻，不是等待 3 s 后的确认时刻。 |
| Completion | `T3 − T0`。UI 仍生成、录屏截止、尾部遮挡、退出状态不明或异常终止时不确认 T3；填 `NA` 并记录观察结束时刻与原因。3 s 窗口不证明服务端/协议已完成。 |
| 可见交互完成 | `yes`：按上条确认正常完成；`no`：明确观察到错误/取消/异常终止且未正常完成；`uncertain`：仍生成、观察截止或状态不可判读。后两者 Completion 为 NA。不是“网络成功”。 |
| 指令满足 | 独立逐项核查固定任务，填 `yes / no / uncertain`；不得从 Completion、停顿或可见完成自动推导。无法完整观察答案时保留 uncertain，不猜未见内容。 |

崩溃、错误和取消保留可见事实；不补跑、不归因网络。若发现人为改变网络或已有 VPN/隧道/shaping，停止并记不满足 C0；不要自行清理未知会话。无法固定锚点、条件或可靠观察时，记录未执行/受影响指标缺失，不伪造正常完成。

### 时间区间，不伪造精度

起点在 `[A1,A2]`、终点在 `[B1,B2]` 时，时间差区间为 `[time(B1)−time(A2), time(B2)−time(A1)]`。TTFR、TTFC、Completion、停顿和稳定窗口均按此传播，不取中点冒充确定值。

- 停顿区间下界 `≥2.0 s` 才确认；上界 `<2.0 s` 为未达约定；其余为 `uncertain`。
- 完成稳定观察时长的下界须 `≥3.0 s`；区间跨界或只有不足 3 s 的观察都不能确认 T3。
- 没有可靠视频帧→时间戳映射，不假设帧率；保留帧区间，所有秒数字段填 `NA`。事件顺序也不确定时保留不确定，不截断为零或推算。

## 与 Prototype 0.1 的概念对应：不可数值互换

［KNOWN｜HIGH］以下依据[冻结的 0.1 指标说明](../prototype-0.1/03_METRICS_SCORING_SPEC.md)。只是帮助读者理解两个观察层，不修改任一公式。

| 人工观察 | 0.1 合成观察 | 不等价边界 |
|---|---|---|
| 可见 TTFR / TTFC，起点为屏幕发送锚点 | 从 Android 发起传输到首个合规 SSE content 的 TTFT | 可见 UI 与解码事件不是同一时钟/起点；不能替代模型推理时间。 |
| 最后正文更新与 UI 完成代理 | 匹配 terminal done 的 Completion | 画面稳定不是服务端或协议回执。 |
| 恢复后的完整正文更新间隔，人工 2 s 约定 | 相邻合规 SSE 间隔超过 `max(500 ms, 4×nominal interval)`；停顿时长按超出 nominal 部分计算 | 事件、阈值、不确定度和时长口径不同，不能合并统计。 |
| 可见完成与独立指令满足 | 120 个有序匹配事件及合规 done 等协议成功条件 | 不是同一 Success Rate；不据此生成 RPI。 |

［INFERRED｜HIGH］同 App/任务/可见模式与 C0 三次重复减少部分操作差异，但不能分离模型、服务端、设备、UI、缓存及网络的贡献；不可见模型路由仍 UNKNOWN。三次不是因果对照，也不建立统计置信区间。回答内容本身不得用来反证或证明网络要求。
