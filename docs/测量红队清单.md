# ANEB Probe 测量红队清单（redteam v0.1）

> 生成方式：多代理红队工作流——4 个视角（SSE 流式计时 / 时钟与归因 / Android 平台与环境 / 统计与结果合同）并行枚举 48 项候选风险 → 合并去重为 35 项 → 每项由独立怀疑论代理对照设计文档与 KPI 文档逐条对抗验证。
> 结果：**32 项确认 / 3 项驳回**。日期 2026-07-12。
>
> 本清单是测量效度的权威闭环追踪表（对应参考项目的 RED_TEAM_CLOSURE 制度）。每项风险的闭环动作已按"闭环阶段"归入《ANEB Probe 开发设计文档》第 8 节各阶段验收；开发中每闭环一项，在本表"闭环状态"栏更新并在 evidence/ 留证。
>
> **实测增补（2026-07-13）**：真机首测战役新增一条经真实蜂窝实证的中间盒行为条目 **R-33（运营商 SNI-keyed TLS RST 注入）**，编号续于红队 32 项之后并标注为「实测发现」——它非 4 视角枚举所得，而是 ELS-AN00 电信 5G SA 真机现场 A/B 证据入册。该条目描述的是**测量对象本身**（可量化的中间盒 TLS 干预维度）而非工具缺陷，缓解与研究正当性边界见《DECISION_LOG》D-22 双通道决策；其与 R-05/R-03（中间盒缓冲、代理劫持）同族但触发键与后果不同（一按 SNI 内容触发双向 RST、直接阻断握手，非缓冲重塑 ITL）。

## 详细条目

### R-01 requestNetwork(CELLULAR) 绑定不完整且缺 VALIDATED 就绪检查：DNS 走错网、异步竞态、绑定失效静默回退、未验证网络样本被当正常数据

- **视角**：Android 平台与环境　**严重度**：high　**影响**：N1/N2/T1/U1/R1　**闭环阶段**：阶段0
- **失真机理**：绑定有多个缺口：(1) OkHttp 只换 socketFactory 而不把 Dns 接口换成 network::getAllByName 时，域名解析仍走默认网络（WiFi）的 DNS，解析与承载路径分裂，dnsStart/dnsEnd 计时归因错误；(2) requestNetwork 的 onAvailable 异步，WiFi 未关时蜂窝 Network 可能数秒才起（用户关「始终开启移动数据」时永不到来），守卫超时兜底放行则实际走了 WiFi；(3) 蜂窝重连/制式迁移后旧 Network 失效，OkHttp 单例 socketFactory 未重建则后续场景绑定悄然作废；(4)「关 WiFi 后立即开测」路径上，系统对蜂窝网络的连通性验证（NET_CAPABILITY_VALIDATED）需数秒，期间 DNS 切换、首连接额外排队——守卫只做网络类型确认没有 VALIDATED 检查，会在未就绪状态产出 TTFT/RTT 偏高的「合法」样本；运营商偶发重定向/portal 场景下 8443 直连可能被劫持到门户。客户端自己拿到的 network handle 无法自证流量真走了蜂窝。
- **缓解措施**：NetGuard 实现：Dns 用 network::getAllByName；onAvailable 拿到且 NetworkCapabilities 同时含目标 transport + NET_CAPABILITY_VALIDATED + NOT_SUSPENDED 后才放行（无超时放行，超时如 15s 则 fail-closed 报环境不就绪），关 WiFi 与开测之间强制该等待而非固定 sleep；连接建立后比对 socket localAddress 是否属于目标 Network 的 LinkProperties 地址；服务端每响应回显 observed 源 IP，客户端与运营商出口段核对存档，源 IP 归属与声称 transport 不符即判无效——绑定证据做成双端对账而非客户端自证；/echo 响应校验服务端指纹头（自定义 header + 证书 pin），响应不带指纹即判路径劫持而非计入失败率。
- **对抗验证结论**：设计文档仅在 4.6 条与第 9 节风险表写了「requestNetwork(CELLULAR) 绑定 socket」和「目标网络类型确认」，未提 OkHttp Dns 接口须换成 network::getAllByName（否则解析走默认网 DNS，dnsStart/dnsEnd 及 N1/T1 归因错误）、未要求 NET_CAPABILITY_VALIDATED/NOT_SUSPENDED 就绪检查（「关 WiFi 后立即开测」会产出 TTFT/RTT 偏高但被判合法的样本）、未规定 onAvailable 异步等待的 fail-closed 策略与网络失效后 socketFactory 重建（5.2 的 OkHttp 单例+每场景新建连接不覆盖 Network handle 失效），且「受污染」标只对已检查项生效，DNS 分裂与未验证网络在现有检查下不可检测——对以蜂窝取证为核心目的的工具这是静默失效的效度风险；唯 8443 portal 劫持一条被 TLS 证书校验天然弱化（劫持表现为连接失败而非伪样本），属次要。

### R-02 无线层采样陈旧且时戳滞后：1Hz 拿到的是 modem 缓存重复值，stall 与切换的因果排序可能颠倒

- **视角**：Android 平台与环境　**严重度**：high　**影响**：R1/T3/T4　**闭环阶段**：阶段1
- **失真机理**：Android 的 CellInfo/SignalStrength 是 modem 节流的缓存上报：getAllCellInfo 常返回带旧 timestamp 的缓存（省电状态更新周期可拉长到数秒），1Hz 写入的可能是同一份缓存重复十次——radio 曲线看似平滑连续，实际分辨率只有 0.2Hz，stall 事件被对齐到「信号良好」的陈旧样本上得出错误归因；定位服务总开关关闭时 CellInfo 直接返回空。同时回调触发时刻打的戳可能比信息实际生成时刻（CellInfo.getTimestampNanos）晚数百 ms 甚至秒级，用回调到达时刻对齐时，一次 800ms 的 stall 与一次 PCI 变更的先后关系完全在噪声之内——「切换导致卡顿」的因果链可能实际是卡顿在前、上报在后，取证结论被时序假象支撑。
- **缓解措施**：每次采样用 requestCellInfoUpdate 主动触发刷新而非被动读缓存；RadioSample 同时落两个戳：CellInfo.getTimestampNanos（信息时刻，换算到 elapsedRealtime 轴）与回调到达时刻，对齐一律用前者，两者差值入库作为上报延迟协变量；采样时刻与 modem 时间戳差 >2s 的样本打 stale 标，stall 归因只允许用 fresh 样本；切换事件不做点事件归因，给 ±max(上报延迟P95, 1s) 的归因窗口，stall 落在窗口内只标「疑似相关」；报告模板用窗口重叠表述并标注窗口宽度，禁止精确到毫秒的因果叙述；守卫增加 LocationManager.isLocationEnabled 检查（与权限检查分开），权限被拒时 R1 输出显式 permission_denied 状态而非空表。
- **对抗验证结论**：Android 平台事实成立：SignalStrength/CellInfo 是 modem 节流缓存（更新周期常为数秒，1Hz 写入即重复值），minSdk 29 下设计未要求 requestCellInfoUpdate 主动刷新、未采用 CellInfo 自带时间戳（getTimestampNanos/Millis 与 elapsedRealtime 同轴却被忽略）、无 stale 标记与归因窗口；而 KPI 5.3.5 的明确用途恰是"把 stall/中断归因到切换"，设计文档 4.5 仅笼统写"1Hz 采样+按单调时间轴对齐"，4.6 守卫也缺定位总开关检查（Android 10+ 定位关闭时 getAllCellInfo 返回空，取证跑完 R1 静默为空）——虽然 T3/T4 数值与 AQS 本身不受污染，但"Android 才能拿无线层"是本项目选型根基、切换因果归因是取证核心叙事，秒级时戳滞后足以颠倒 800ms stall 与 PCI 变更的先后，现有条款（5.3.1/5.3.5、设计 4.5/4.6）均未闭环该风险。

### R-03 VPN/私有 DNS/WiFi 代理劫持路径：「直连裸端口 8443」假设静默失效，本地 VPN 批化被记成运营商中间盒证据

- **视角**：Android 平台与环境　**严重度**：high　**影响**：N1/N2/T1/T2/T3/AQS　**闭环阶段**：阶段1
- **失真机理**：设计用「非标端口 8443 直连、不挂 CDN/反代」对抗中间盒缓冲，但守卫清单没有任何 VPN/代理检查。AdGuard 类本地 VPN、工作 profile 企业 VPN、WiFi 配置的 HTTP 代理、Private DNS(DoT) 会让 /echo RTT 与 SSE 流全程走隧道（N1/N2 测的是 VPN 网关路径）；本地 VPN 的用户态转发天然引入批化，触发自检后被记成「运营商中间盒缓冲」的取证证据；且 requestNetwork(CELLULAR) 拿到的底层 Network 会绕过 VPN，造成蜂窝场景不走 VPN、WiFi 场景走 VPN 的隐性不对称，S1 vs S2 对照失去意义。
- **缓解措施**：守卫增加三项硬检查并 fail-closed：getActiveNetwork 的 NetworkCapabilities 含 TRANSPORT_VPN 或存在 VPN 类 Network 即拒测；LinkProperties.getHttpProxy()/ConnectivityManager.getDefaultProxy() 非空即拒测；LinkProperties.isPrivateDnsActive() 记入元数据（DoT 不必拒测但 dns 计时须标注 claim scope 为「至 DoT 服务器」）；服务端记录 TLS ClientHello 指纹与源 IP，异常变化作为透明代理的辅助证据。
- **对抗验证结论**：设计文档4.6节守卫清单只检查屏幕常亮/前台Service/省电模式/网络类型绑定，KPI文档5.3.6也仅要求前台+常亮+关省电，均无任何VPN(TRANSPORT_VPN)、HTTP代理(LinkProperties.getHttpProxy)或Private DNS检测；风险技术前提全部成立——OkHttp默认走ProxySelector会吃到WiFi代理配置、本地VPN的用户态转发引入的批化若低于4.4节">30% ITL≈0"阈值会静默抬高N1/N2/T2/T3而元数据中无VPN标记导致事后不可剔除、若超阈值则按4.4/第9节风险表的叙事被归因为"中间盒/运营商代理缓冲"造成取证误归因，且requestNetwork(CELLULAR)绕过VPN而默认网络(WiFi)不绕过的隐性不对称确为Android真实行为，设计文档第9节"蜂窝流量走WiFi"条目恰好只固化了这一不对称的一半；对一个以"数据质量与可重复性>一切"并以向运营商举证为使命的工具，这是低成本可修的高价值缺口（DoT部分影响较小，因T1从请求末字节起算、N1为已建连接RTT，风险中该子项偏轻但记元数据的建议合理）。

### R-04 SSE 读实现的双向失真：合帧/读线程调度使 ITL≈0 稀释 P95，逐字节解析又把 App 开销记成网络间隔

- **视角**：SSE 流式计时　**严重度**：high　**影响**：T2/T3/T4/AQS　**闭环阶段**：阶段0
- **失真机理**：打戳时刻是「从 okio 缓冲读出」而非 socket 到达：H2 专属读线程先将 DATA frame 写入 stream 接收缓冲，一个 TLS record 携带 2~3 个 SSE event（S2 簇内 100 tok/s、间隔 10ms、payload ~120B 极易合帧）时，第 2..n 个 event 的「首字节时刻」是内存读出的 CPU 时刻，ITL≈0；客户端读线程被 Android 调度抢占/GC/降频时也产生同样形态。这些 0 值样本混进 T2 的 P95 会稀释分位数让 T2 虚好，批间被拉大的间隔又推高 T3 stall 率——同一失真让一个 KPI 虚好、另一个虚差，AQS 加权和看似正常，且 30% 以下批化不触发自检。另一方向：为避免 okhttp-sse 整 event 回调偏差而做的「逐字节 read」，每 event 数百次方法调用叠加 JIT 抖动，中低端机上解析耗时毫秒级并推迟下一 event 的读出时刻，把解析成本记成网络 ITL。
- **缓解措施**：实现改为「按可用量批读（source.read(buffer, 8192)）+ 在字节缓冲内扫描 event 边界」：一次 read 打一次戳，同批 event 共享块首到达时戳并标 same_read_batch/batch_id=true，杜绝伪造 0ms 间隔；批化检测从二值判无效降为逐间隔标注（ITL<1ms 标 coalesced），coalescing 率作为运行元数据；T2/T3 输出「含 coalesced」与「合帧组内只保留组首间隔」两个口径并列报告，禁止 0 值样本参与 P95；读线程 setThreadPriority(THREAD_PRIORITY_URGENT_AUDIO)，客户端哨兵线程量化本机调度抖动，超阈值打 client_sched_suspect 标；阶段 0 用环回跑 profile 验证解析层自身耗时 P99<1ms 并存 evidence/；阶段 1 netem 验收加一条：服务端故意合并 flush 制造 20% 批化，验证剔除口径下 T2/T3 统计不漂移。
- **对抗验证结论**：OkHttp H2 架构下应用层读出时刻≠socket到达时刻是结构性事实，S2 簇内 10ms/120B 参数恰好最易合帧，ITL≈0 稀释 T2 P95 同时推高 T3 形成双向失真；现有条款（设计 4.4/KPI 5.3.3 的 30% 二值批化自检、5.3.4 节奏剥离、阶段0 P95<10ms 验收）只覆盖中间盒缓冲与服务端误差，对亚阈值合帧稀释、客户端读线程调度批化、逐字节解析开销计入 ITL 均无标注/修正/预算条款，未闭环。

### R-05 批化自检二值阈值双向骗人：蜂窝 TTI/C-DRX 真实聚合被误判为中间盒缓冲致弱网样本系统性判无效，亚阈值缓冲又混过校验

- **视角**：SSE 流式计时　**严重度**：high　**影响**：T2/T3/T4/AQS/R1　**闭环阶段**：阶段1
- **失真机理**：「>30% ITL≈0 且随后跟长间隔判无效」的判据双向失效：(a) LTE/NR 空口本身按 TTI/调度机会成批投递下行小包，C-DRX 下 UE 按 onDuration 周期醒来收数据——弱覆盖下 token 天然微批到达，模式与中间盒缓冲高度相似，信号越差的运行越容易被判无效丢弃，留下的数据集偏向好网，AQS/T3 虚好，而弱网证据恰是核心价值；(b) 中间盒轻度缓冲（攒 2–3 个 token 或 20–50ms 小缓冲）产生 20% 近零间隔，低于阈值判「有效」，但 ITL 分布已被重塑带病进 AQS；(c) S2 profile 自身的簇内 100 tok/s + 簇间 300–800ms 停顿正是「近零间隔后跟长间隔」形态，合法样本可能被误杀，且误杀率与设备计时粒度相关，不同手机的有效样本率不可比。
- **缓解措施**：检测器改在服务端节奏剥离后的残差域运行（「负残差簇+正残差尖峰」锯齿才是缓冲证据，profile 设计内的突发节奏天然被剥离不误触发）；自检从二值改为分级标注并永远保留原始数据，输出连续 buffering_score（残差自相关/锯齿占比）随结果存档，阈值留待数据回流后标定；增加区分性特征：批间隔周期性谱分析（DRX/调度周期呈 8/10/20/40ms 离散特征，中间盒缓冲呈连续或 RTT 相关特征）+ 与 R1 无线快照联动（信号差+批化→倾向空口聚合；信号优+批化→倾向中间盒）；用已知无中间盒的 WiFi 直连、已知有代理的路径、已知缓冲反代（nginx 默认配置）各采签名样本校准判据后存 evidence/。
- **对抗验证结论**：设计文档4.4与KPI文档5.3.3的批化自检确实定义在原始到达域且为二值判无效：弱覆盖下HARQ/RLC重传、TCP队头阻塞释放与C-DRX唤醒（尤其S2的think_pause 2-5s和簇间300-800ms停顿后首批token）天然产生"长间隔+近零ITL簇"形态，恰与判据重合，会系统性丢弃最有价值的弱网样本（幸存者偏差使AQS/T3虚好），而亚阈值中间盒缓冲（~20%近零间隔）又能带病通过；已有的5.3.4节奏剥离仅用于T2的ITL计算、未应用于自检（4.4明说"检测token到达的批化特征"），第9节风险表反而依赖"4.4判无效"闭环中间盒风险，第9节末行的门限重标定条款针对KPI门限而非自检判据、也不解决二值判废与空口聚合vs中间盒的混淆问题；第7节Room全量存TokenEvent仅缓解数据永久丢失，未定义无效样本在AQS/上报聚合中的处理——风险成立且现有条款未闭环，建议按残差域检测+分级buffering_score+R1信号联动区分的方向修订（(c)子项较弱：簇内100tok/s即10ms间隔在elapsedRealtimeNanos下不会被误认为ITL≈0，除非叠加空口聚合，但这正好又回到(a)）。

### R-06 网络回压时拥塞被剥离进服务端节奏，最恶劣样本反被 flush 误差自检判失真剔除

- **视角**：SSE 流式计时　**严重度**：high　**影响**：T2/T3/T4/AQS　**闭环阶段**：阶段1
- **失真机理**：下行真拥塞（弱网、缓冲膨胀）时内核 send buffer 填满 → Flush 阻塞 → 服务端「实际 flush 时刻」整体推迟且挤压——若 srv_ts 记实际 flush 时刻，服务端发出间隔本身已被网络拉大，「到达间隔−发出间隔」的对齐差反而变小，网络劣化被剥离进服务端节奏而漏计（T2/T3 虚好）；同时 flush 误差 P99>5ms 自检触发，把这次运行标为「服务端失真样本」剔除。净效果：网络越差的样本越容易被丢弃或低估，AQS 与弱网灵敏度验收（netem 100ms/1% 应使 T2/T3/T4 恶化）出现方向性偏乐观或虚假通过。
- **缓解措施**：服务端把 pacing 误差拆成两类分别记录：timer 迟到（调度问题，判服务端失真）与 flush 阻塞时长（网络回压证据，绝不判失真、随流返回作为归因数据）；每 event 同时携带期望发出时刻（profile 时刻表）与实际 flush 时刻两个戳，网络贡献以期望时刻为基准计算、以 flush 阻塞时长做修正项；netem 灵敏度验收中显式核对「注入劣化未导致样本被判无效」。
- **对抗验证结论**：Go 写阻塞机制对本设计真实成立：srv_ts 记实际 flush 时刻（设计文档4.3自检口径证实），TCP 回压时网络劣化被剥离进服务端节奏使 T2/T3 虚好，且 P99>5ms 自检无因区分会把最恶劣 stall 样本判服务端失真剔除（第9节风险表仅归因 VM 抖动，强化了误判）——形成针对最差网络样本的系统性幸存者偏差；唯一修正是 netem 100ms/1% 下流速仅约10KB/s 远低于 Mathis 上界，验收本身不易触发，真正触发场景是数秒级 stall/缓冲膨胀，即工具核心取证对象，故隐蔽性更高；现有条款未闭环，建议的双时间戳+阻塞/迟到拆分+验收核对项均必要。

### R-07 上行逐块打戳测的是写入 socket buffer 的速度：U1 计时终点选错则整体虚高一档以上

- **视角**：时钟与归因　**严重度**：high　**影响**：U1/U2　**闭环阶段**：阶段0
- **失真机理**：「RequestBody.writeTo 手动分块写并逐块打戳」——但 write 在内核 send buffer 未满前立即返回：512KB–1MB 的 prompt 在默认 SO_SNDBUF 下前一大半块的「耗时」只是内存拷贝，逐块序列前段测出千兆级假吞吐。若 U1 goodput 终点取 requestBodyEnd（最后一字节写完）而非服务端确认，整个 1MB 可能都还在本机与网络缓冲里，U1 直接虚高一档以上（20Mbps 门限档位差 4 倍）。客户端写序列与服务端逐块到达序列跨端对齐还要注入 ±RTT/2 与漂移误差。
- **缓解措施**：U1 计时终点定义为收到服务端 2xx 响应头（服务端已读完 body）时刻，单端可测不依赖 offset；服务端 /upload 返回的逐块到达时间序列作为上行节奏的权威序列（只用其间隔，不做跨端绝对对齐），客户端 writeTo 序列 claim_scope 显式标注为「写入本地协议栈」仅作辅助诊断；缩小 SO_SNDBUF 或用背压感知写法让写返回贴近线上发出；阶段 0 验收：同 WiFi 下 U1（响应确认口径）与 iperf3 同向吞吐偏差 <20%。
- **对抗验证结论**：风险真实成立：设计文档第5节明确用 RequestBody.writeTo 逐块打戳"得到上行吞吐时间序列"，第4节计时点列表含 requestBodyEnd，但两份文档均未定义 U1 的计时终点口径——而 Android tcp_wmem 上限（常见 4MB+）与 Go http2 服务端默认 ~1MB 流窗口意味着整个 1MB body 可在服务端读完前全部写入本地/在途缓冲，requestBodyEnd 口径下 U1 系统性虚高一档以上（20Mbps 档界差 4 倍），且 U1 占 AQS 15% 权重；第6节 /upload "响应返回服务端视角的接收时间序列"提供了正确测量的原料，但没有任何条款把 U1 计算绑定到该序列或"收到 2xx 响应头"口径，第4.4/9节的反缓冲自检只覆盖下行 SSE，阶段0验收（ITL 对齐 P95<10ms）也不校验 U1，故属未闭环的高危测量失真。

### R-08 客户端-服务端事件按数组索引配对而非按 seq join：丢一个 event 全场静默错位

- **视角**：时钟与归因　**严重度**：high　**影响**：T2/T3/T4　**闭环阶段**：阶段0
- **失真机理**：设计说「逐序号对齐差」，但实现最容易写成 zip(client_events[i], server_intervals[i])。客户端 SSE 解析器是自实现的约 100 行逐字节读，payload 为对数正态随机字节，一旦半包边界处理有 bug 静默丢弃或错切一个 event，后续全部 client[i] 对上 server[i+1]——整段「网络抖动」序列完全错配但数值看起来合理（不会 NaN、不会崩），T2/T3/T4 全军覆没且无告警。
- **缓解措施**：KpiCalculator 强制以 event 内嵌 seq 字段做 join，禁止位置配对；检测 seq 缺号/重号/回退，gap_count>0 即打降级标，gap 超过 token 总数 1% 判样本无效（fail-closed）；payload 用长度前缀或 base64 编码，杜绝随机字节与 SSE 分隔符（\n\n）冲突的解析歧义；阶段 0 加对抗测试：服务端故意注入畸形/截断 event，验证客户端要么正确跳过并计 gap、要么判无效，绝不静默错位。
- **对抗验证结论**：设计仅在 KPI 5.3.4/设计文档 §4.3 声明"逐序号对齐"的意图且 event 已带 seq，但全文无强制以 seq 为 join 键的条款、无 seq 缺号/重号检测与 fail-closed 判无效规则、payload 为未编码随机字节存在与 SSE \n 分隔符冲突的解析歧义、阶段 0 验收（干净 WiFi + seed 固定字节流）无法暴露路径相关的半包边界 bug——自实现逐字节解析器一旦丢/错切一个 event 即整段静默错位，T2/T3/T4 全错且无告警。

### R-09 T3/T4 stall 率的分子口径歧义：S2 场景设计内的 300–800ms 停顿按原始间隔会被记成卡顿

- **视角**：统计与结果合同　**严重度**：high　**影响**：T2/T3/T4/AQS　**闭环阶段**：阶段0
- **失真机理**：T3 定义是「ITL >200ms 的间隔占比」、T4 是「ITL >1s」，而 KPI 文档只对 T2 明确「已剔除服务端节奏误差」。S2 profile 故意注入簇间停顿 300–800ms 和 think_pause，若 T3/T4 按原始到达间隔计算，这些设计节奏全部 >200ms 必然计入 stall——S2 的 T3 被场景自身灌爆到「差」档，通过 20% 权重和 T4 一票否决（封顶 54 分）拖垮 AQS，测出来的是 profile 设计而不是网络。反过来若实现者悄悄改成对齐差口径，又与 KPI 文档字面定义不符，两端/两人实现得出完全不同的 stall 率。
- **缓解措施**：agent-qoe-kpi 文档升 v0.1.1：T2/T3/T4 一律基于逐 seq 对齐的网络贡献残差（client 到达间隔 − srv_ts 发出间隔）计算，并明确停顿相邻间隔如何配对（seq 对齐而非位置对齐）；KpiCalculator 单测放一个「纯本地回环 + S2 profile」金样本，断言 T3≈0——不为 0 即口径实现错了；阶段 0 验收（对齐差 P95<10ms）顺带验证此口径。
- **对抗验证结论**：KPI 文档 5.1 中仅 T2 括注引用 5.3.4 节奏剥离，T3/T4 字面仍是原始 ITL 口径；S2 profile 的 300–800ms 簇间停顿（geom_p=0.05，期望每 20 间隔 1 次）使原始口径 T3 基底恰为 ~5% 压在「可/差」线上、纯净网络亦然，且无「纯本地回环 T3≈0」金样本断言，口径歧义未被任何现有条款闭环（T4 一票否决部分有夸大：设计停顿 ≤800ms 不直接过 1s 线，但叠加网络时延后仍受污染）。

### R-10 失败/超时/断流与失真标记样本的统计去向未进结果合同，叠加弱网上报失败制造数据集级幸存者偏差

- **视角**：统计与结果合同　**严重度**：high　**影响**：T1/T2/T3/T4/U1/U2/N1/C1/AQS　**闭环阶段**：阶段0
- **失真机理**：设计从未定义：SSE 流在第 200/800 token 断掉时 T1/T2/T3 用截断样本算还是整场景判失败？TTFT 超时记 null、记 30000ms 还是不产生记录？/upload 中途失败 U1 怎么记？同时存在三种「坏样本」标记（服务端发送误差失真、守卫污染、批化无效），但没有任何一处规定带标样本是否进 KPI/AQS/跨 run 聚合——标了仍统计则标记形同虚设，静默剔除则口径样本量失守。若失败/带标场景被静默丢弃、AQS 只在「跑完」的场景上算，恰恰在网络最差（最值得取证）的时刻产生幸存者偏差，弱网下 AQS 系统性虚高。再叠加一层：「测试结束上报服务端落 JSONL」在弱网/断网时最可能失败，而这正是最有价值的样本——服务端数据集系统性缺失最差网络的 run，后续基于 JSONL 的「分布分位数重标定门限」建立在被删节的分布上，门限被校准得过于乐观。
- **缓解措施**：阶段 0 定义结果合同 JSON schema：每个 KPI 值 nullable，附 sample_count/expected_count/failure_reason（失败样本记 null 绝不记 0）；场景级三态 Gate（valid / valid_low_confidence / invalid），invalid 时 KpiValue 为空数组而非 0 值；断流场景保留部分 TokenEvent 明细但 KPI 置 null；标记语义显式分级：invalid（不进任何统计，但 run 记录保留并计入 invalid_rate）/ tainted（进统计但输出携带标记，AQS 加受污染水印）；AQS 仅在全部权重项 valid 时输出，否则输出「AQS 不可计算」+原因码；Uploader 实现持久化重试队列（Room 存 pending 状态，联网自动补传），重标定分析脚本强制校验客户端导出 run_id 集合与服务端 JSONL run_id 集合差集为零；用 netem 100% loss / 中途 kill server 两个用例做合同回归测试。
- **对抗验证结论**：逐条核对属实：设计文档 4.3/4.4/4.6 与 §7 确实定义了三种坏样本标记（服务端失真、污染标志、批化无效）和 ScenarioResult 的"有效性标志"，但全文（含 KPI 文档 5.3/5.4）没有任何条款规定带标/失败/断流样本在 KPI、AQS、取证模式中位数、跨 run 聚合中的统计去向——SSE 中途断流时 T1–T4 用截断样本还是判场景失败、TTFT 超 readTimeout 30s 记什么、U1 的"≥3 次取中位数"缺样本怎么办均未定义（C1 能记中断次数但属阶段二且不解决 MVP 截断口径）；上报仅为"测试结束 POST /results"无重试队列，弱网 run 最易缺失于服务端 JSONL，而 §9 恰以"数据回流后分布分位数重标定"依赖该数据集，幸存者偏差链条成立。部分缓解仅有"双写"（Room 全量+本地导出）保证原始数据不灭失，但无客户端/服务端 run_id 对账要求，分析管线偏差未闭环。鉴于文档自述取舍原则是"数据质量与可重复性 > 功能覆盖"，且阶段 1 验收用例全部只覆盖跑通路径，此缺口直接命中项目核心价值，判高严重度。

### R-11 热节流降频使打点线程系统性滞后：客户端侧无「发送误差自监控」的对称机制，越测越热造成场景后段网络变差的假象

- **视角**：Android 平台与环境　**严重度**：medium　**影响**：T1/T2/T3/T4/N1/N2　**闭环阶段**：阶段0
- **失真机理**：设计只剥离服务端节奏误差，对客户端完全没有对称机制。90 秒 5G 流式+屏幕常亮+LiveScreen 渲染让 SoC 快速热节流，CPU 降频后 SSE 读线程被调度延迟：字节已到内核缓冲但用户态「读到首字节时刻」系统性滞后。client_ts 偏晚直接抬高 T1/T2/T3，且随测试进行单调恶化；/echo 的 20 次 RTT 采样若在冷机、流式阶段在热机，时钟 offset 归因也随之失真。
- **缓解措施**：做客户端版的发送误差自监控镜像：(1) PowerManager.addThermalStatusListener 记录热状态迁移事件进时间轴，THERMAL_STATUS_SEVERE 以上打污染标；(2) 每秒读 /sys/devices/system/cpu/*/cpufreq/scaling_cur_freq 存入 RadioSample 同表；(3) 读线程 setThreadPriority(THREAD_PRIORITY_URGENT_AUDIO)；(4) 阶段 0 验收增加「手机预热到 SEVERE 后重测」对照，量化热节流对打点的贡献上限并写入方法学文档。
- **对抗验证结论**：不对称性属实：设计只剥离服务端节奏误差（5.3.4/设计4.3），客户端无热状态记录或打点自监控，且5.3.6强制屏幕常亮+LiveScreen实时渲染+5G流式本身制造热负载，取证模式约12分钟单调升温确为未记录的混杂因子；但风险量级被夸大——ITL/stall类指标(T2-T4)对恒定滞后天然差分抵消（只有调度抖动泄入，通常为毫秒级、远小于门限），且clock_sync按profile schema是每场景前执行而非仅冷机一次，offset归因失真上限约90秒漂移，故判成立但严重度为中，建议采纳热状态打点与污染标机制。

### R-12 有效性守卫只在测前检查一次：Doze/厂商省电在测中生效，设备侧冻结被误归因为运营商中间盒

- **视角**：Android 平台与环境　**严重度**：medium　**影响**：T2/T3/T4/AQS　**闭环阶段**：阶段1
- **失真机理**：屏幕常亮、前台 Service、非省电模式等守卫是测试前一次性快照，但 S2 长 90s、取证模式约 12 分钟，MIUI/ColorOS/OneUI 的后台限网、App Standby Bucket 降档、Doze 边缘状态可在测中途生效：socket 数据被延后成批交付，SSE 读线程被冻结数百毫秒后一次性读到多个 event。表现为「长间隔+一串 ITL≈0」，被计入 T2/T3/T4 拉低 AQS，且批化自检会把它误归因为「链路存在缓冲/运营商中间盒」——把设备侧问题当成网络证据，对取证工具是反向污染。
- **缓解措施**：守卫从一次性检查改为测中持续监控并写入事件时间轴：监听 PowerManager.ACTION_DEVICE_IDLE_MODE_CHANGED / isPowerSaveMode 变化、ActivityManager.isBackgroundRestricted、UsageStatsManager standby bucket；另加 1Hz 本地「调度心跳」（Handler postDelayed 期望 vs 实际执行时刻），心跳误差尖峰与 ITL 尖峰对齐即可区分「设备侧冻结」与「链路缓冲」；任一测中事件触发即 fail-closed 打污染标（首事件获胜状态机），结果里区分 device_side_batching 与 link_batching 两种无效原因。
- **对抗验证结论**：守卫确为测前一次性快照（设计 4.6、KPI 5.3.6），取证模式 12 分钟内国产 ROM 限网/Doze 边缘可致读线程冻结，其"长间隔+ITL≈0 批"签名与中间盒缓冲不可区分，而 4.4 批化自检与 §9 风险表把该签名单向归因为"链路缓冲/中间盒"，构成取证反向污染；不过 fail-closed 判无效已防止分数污染，主要损害是成因误标与阈下轻度冻结漏入 T2/T3/T4，故判 medium，建议采纳测中持续监控+调度心跳+双成因区分的缓解方案。

### R-13 双卡设备智能切卡：数据承载 SIM 中途改变，RadioCollector 监听错卡、信号曲线与实际路径脱钩

- **视角**：Android 平台与环境　**严重度**：medium　**影响**：R1/T4/AQS　**闭环阶段**：阶段1
- **失真机理**：双卡机的「智能选择数据卡」会在信号劣化时把数据承载切到副卡（含临时数据切换）。RadioCollector 若按默认方式注册 TelephonyCallback，监听的是 default subscription，切卡后 R1 记录的 RSRP/SINR/PCI 属于不承载数据的那张卡；TestRun 元数据的运营商/APN 是开测时刻快照，切卡后整场数据挂错运营商名下；切卡瞬间蜂窝 Network onLost/onAvailable，流式中断被记为网络问题实为终端策略。对运营商 A、B 横比取证时这是最容易被质疑的数据混淆。
- **缓解措施**：RadioCollector 通过 SubscriptionManager.getActiveDataSubscriptionId 确定当前数据卡，用 TelephonyManager.createForSubscriptionId 注册回调；注册 ActiveDataSubscriptionIdChangedListener，测中切卡即打污染标并在时间轴记事件；RadioSample 每行带 subId；守卫文档化建议测试期临时关闭智能切卡/禁用副卡数据。
- **对抗验证结论**：真实成立：设计文档 §4.5/§5（radio/ RadioCollector）与 KPI 文档 5.3.5 均只写"TelephonyCallback 1Hz"，未用 SubscriptionManager.getActiveDataSubscriptionId + createForSubscriptionId 绑定数据卡，也未监听 DDS 切换；§7 TestRun 的运营商/APN 是开测快照、RadioSample 无 subId；§4.6 守卫与 §9 风险表全文无双卡/SIM 条目（grep 证实），NetGuard 的 requestNetwork(CELLULAR) 只区分蜂窝/WiFi 不区分 SIM。国内双卡+智能切卡普及，且切卡恰在弱信号（最有测量价值的场景）触发，R1/切换归因/运营商标签会被静默污染；定为 medium 而非 high 是因为 T/U 组与 AQS 测的是实际路径、数值本身仍有效，失真限于无线层归因与运营商归属，且按建议缓解（绑 subId + 监听 ActiveDataSubscriptionIdChanged 打污染标 + 守卫提示关智能切卡）成本低，应纳入阶段 1。

### R-14 WiFi 测试无绑定对称性：OEM 智能网络切换/双通道使默认网络中途漂移，三场景 AQS 混合两张网

- **视角**：Android 平台与环境　**严重度**：medium　**影响**：T1/T2/U1/N1/N2/AQS　**闭环阶段**：阶段1
- **失真机理**：设计只对蜂窝测试要求绑定，WiFi 场景走默认网络。小米「双 WLAN 加速」、OPPO/vivo「智能双通道」、各家「WLAN 助理」会在 RSSI 下降或拥塞时把默认网络静默切到蜂窝甚至双路并发。由于「每场景新建连接」，完全可能 S1 在 WiFi 上跑、S2 新建连接时已漂移到蜂窝——三场景 AQS 混合两张网，而 TestRun 元数据只记录一次运营商/APN，事后无法发现。
- **缓解措施**：对称化：无论 WiFi 还是蜂窝都用 requestNetwork(指定 transport) 拿 Network 并以 network.socketFactory 构建 OkHttpClient；registerDefaultNetworkCallback 监控整场测试，network handle 或 LinkProperties 变化即中止当前场景、取消 in-flight 请求、打污染标（fail-closed）；每个 ScenarioResult 存该场景实际所用 Network 的 transport+capabilities+接口名快照，而非 TestRun 级一次性元数据。
- **对抗验证结论**：不对称性属实：设计文档 4.6 与第 9 节风险表仅对"蜂窝测试"要求 requestNetwork(CELLULAR) 绑定且守卫是测前一次性检查，WiFi 场景走默认网络、无 registerDefaultNetworkCallback 全程监控；配合第 5 节"每场景新建连接"，OEM 智能切换（双 WLAN 加速/智能双通道/WLAN 助理）确可使 S1 与 S2 落在不同网络，而第 7 节 TestRun 仅记录一次运营商/APN、ScenarioResult 无每场景网络快照，事后不可发现——现有条款（4.6、5.3.6、9）均未闭环；判 medium 而非 high 是因为 KPI 门限（5.2）声明适用面为蜂窝接入且蜂窝路径已有绑定，WiFi 主要出现在阶段 0/1 验收与对照用途，但该用途下的静默混网仍与"数据质量与可重复性优先"的原则直接冲突，建议采纳所提对称绑定+fail-closed+每场景网络快照缓解。

### R-15 5G NSA 图标语义与实际数据承载不符：R1 制式字段把 LTE 承载记成 5G，是对运营商展示证据时的致命可攻击点

- **视角**：Android 平台与环境　**严重度**：medium　**影响**：R1/AQS　**闭环阶段**：阶段1
- **失真机理**：R1 与 TestRun 元数据用 TelephonyDisplayInfo override 交叉验证制式，但 OVERRIDE_NETWORK_TYPE_NR_NSA/NR_ADVANCED 本质是运营商配置的图标显示策略：NSA 锚定 LTE 时 dataNetworkType 恒为 LTE，图标显示 5G 但 SCG 未激活时数据 100% 走 LTE；反之短暂回落 LTE 时图标可能仍显示 5G。用 DisplayInfo 当承载事实，会把 LTE 路径测得的 KPI 归因为「5G 网络表现」；stall 与「制式变更事件」的归因也会因图标滞后于真实承载切换而错位。
- **缓解措施**：制式字段改为带来源的三元组而非单值：{dataNetworkType, displayInfoOverride, cellinfo_nr_registered}（CellInfoNr.isRegistered，minSdk29 可用），三者一致才输出确定制式，不一致输出 ambiguous 并降低该 run 的归因置信度；对外报告措辞用「设备报告制式」并写入 claim scope——显示态与协商态必须分开记录。
- **对抗验证结论**：成立且未闭环：KPI 文档 5.3.5 明确"NSA/SA 判别用 TelephonyDisplayInfo override 类型交叉验证"，而 OVERRIDE_NETWORK_TYPE_NR_NSA 受运营商 KEY_5G_ICON_CONFIGURATION 图标策略驱动（nrState=NOT_RESTRICTED 即可显示 5G，SCG 未激活时 dataNetworkType 恒为 LTE、数据全走 LTE），设计文档 §7 RadioSample 又把"制式、NSA/SA"存为单值且无不一致/ambiguous 处理，"制式变更事件"归因（5.3.5）也会随图标滞后错位——对以"向运营商展示证据"为使命（设计文档 §1）的取证工具这是真实可攻击点；但严重度限定为 medium 而非风险声称的"致命"：R 组明文"不设门限、仅作归因维度"（5.2/5.1），不进 AQS v0.1 权重（5.4），故 T/U/N 各 KPI 数值与 AQS 分数本身不失真，失真仅在按制式归因/对外表述层；risk 中 affected_kpis 列 AQS 属夸大。建议采纳三元组+ambiguous 降置信方案（注意 CellInfoNr.isRegistered 也只证 SCG 配置而非数据承载，措辞仍须用"设备报告制式"）。

### R-16 工具自己成为干扰源：GC、Room 逐条写与 LiveScreen 实时渲染争抢 CPU，打点线程停顿被全额记为网络 stall

- **视角**：Android 平台与环境　**严重度**：medium　**影响**：T2/T3/T4/N2　**闭环阶段**：阶段1
- **失真机理**：设计要求打点「在回调线程就地记录」但没约束打点线程随后做什么：TokenEvent 是 Room 全量明细（S2 一次 1100+ token、峰值簇内 100 tok/s），若读线程内联构造实体/触发写入，ART 分配与 GC 暂停、SQLite WAL 写入与 fsync 会周期性拖住读线程；LiveScreen「实时 token 瀑布+信号曲线」使测试进行中 Compose 持续重组渲染，与读线程争小核/大核并加剧热节流。读线程被调度出去期间到达的 token 挤在缓冲里，唤醒后成批读出——制造「长间隔+ITL≈0」，污染 T3/T4 并可能误触发批化自检；这类停顿无法用 srv_ts 剥离，全额记账给网络，且干扰强度随设备档次变化，破坏跨设备可比性。
- **缓解措施**：读线程只做「read→elapsedRealtimeNanos→写预分配环形数组（原始 long/int，零对象分配）」，解析、实体构造、Room 落库全部推迟到 phase 结束后一次性批量事务；取证模式 LiveScreen 降为 1–2Hz 摘要刷新或纯文本状态（实时瀑布只留快测模式）；增设哨兵线程以 10ms 周期自旋打戳检测进程级停顿（间隔 >30ms 记 app_jank 事件）并与 token 时间轴对齐，重叠的 ITL 样本标 app_contaminated；Debug GC 计数快照存入运行元数据；阶段 1 验收加「LiveScreen 开/关两种状态下同环境 ITL P95 差 <5ms」。
- **对抗验证结论**：风险真实成立：设计文档 4.1/KPI 5.3.1 只规定「回调线程就地打戳、不经主线程」，未约束读线程打戳后的解析/实体构造/Room 写入负载，也未限制 LiveScreen（5. ui 包，实时 token 瀑布）在测试中的重组频率；S2 簇内 100 tok/s 下读线程被 GC/落库/CPU 争抢拖住时，token 积压在内核 socket 缓冲后成批读出，形成「长间隔+ITL≈0」，srv_ts 节奏剥离（5.3.4）只能剥服务端调度误差、无法剥客户端接收侧停顿，全额记入 T2/T3/T4；4.4 批化自检门限为「>30% ITL≈0」，零星停顿达不到门限却已污染 P95 尾部，且触发时会误归因为中间盒缓冲。现有条款（4.6 有效性守卫查省电/前台/网络绑定；阶段0 验收对齐差 P95<10ms 未规定 LiveScreen 开启状态；9 风险表只覆盖服务端时钟与中间盒）均未闭环该风险。定 medium 而非 high 的理由：工具为研究者自用、设备可控，阶段0 WiFi 对齐验收能暴露粗污染，影响主要在尾部分位数而非系统性偏移；建议采纳缓解项（环形数组零分配打戳+事后批量落库、取证模式降频渲染、哨兵线程 jank 标记、验收加 LiveScreen 开/关对照）。

### R-17 srv_ts 打在用户态 Flush 时刻：Flush() 返回 ≠ 字节离开主机，内核缓冲与 TLS 合帧架空「服务端发出间隔」

- **视角**：SSE 流式计时　**严重度**：medium　**影响**：T1/T2/T3/T4　**闭环阶段**：阶段0
- **失真机理**：Go 的 http.Flusher.Flush() 把数据推过 http2 framer 与 TLS 层写入内核 send buffer 即返回——buffer 未满时 flush 恒「准时」，「实际 flush vs 期望时刻 P99>5ms」自检永远绿灯，而真正发出时刻由内核（GSO 合并、qdisc）决定；srv_ts 写进 event body 的时刻还早于 flush 调用，进一步高估发出间隔的均匀性。S2 burst 簇内 10ms 间隔的多个 event 被合进同一 TLS record/TCP 段同时到达时，到达间隔≈0 而发出间隔=10ms，逐 token「网络贡献」出现负值后跟大正值——T2/T3 分布被双峰化，且批化自检会把服务端自身合帧误判为「链路存在缓冲，样本无效」白丢样本。
- **缓解措施**：srv_ts 语义固定为「Flush() 返回之后」并记录 flush 调用耗时；VM 上调小该连接 SO_SNDBUF（如 64KB）并设置 TCP_NOTSENT_LOWAT（经 syscall.RawConn），让 flush 阻塞语义逼近真实发出；服务端每秒采样 TCP_INFO（tcpi_notsent_bytes/SIOCOUTQ）随流带回，send queue 非空窗口内的 event 打 egress_uncertain 标；「网络贡献为负」的样本不做 clamp-to-zero，原值入库并统计负值占比作为发出时刻可信度指标；阶段 0 验收增加服务端 tcpdump 抓包时戳 vs srv_ts 逐 event 对齐（P95 偏差 <2ms 才可宣称节奏剥离有效），且专门加一组 burst 段验收而非只验均匀流。
- **对抗验证结论**：核心成立：设计文档§4.3/KPI§5.3.4 的"实际 flush 时刻 vs 期望时刻"自检只覆盖 flush 调用前的调度误差，对写入内核后的发出延迟（qdisc/vhost/GSO）盲视，buffer 未满时恒绿；§8 阶段 0 验收用均匀流+10ms 门限+srv_ts 自证，覆盖不到 S2 burst 簇内 10ms 段也无独立时戳地面真值，§4.4 批化自检无法区分服务端合帧与链路缓冲会误归因丢样。但"10ms 间隔 event 合进同一 TLS record"子项夸大（每次 Flush 独立 record、NODELAY 下健康路径逐段即发，到达端双峰多为路径排队即正确归因的网络贡献），且独享 VM 下残余误差典型亚毫秒~低毫秒、相对 T2/T3 百毫秒级门限影响有限，故判 medium；建议采纳 tcpdump 对齐验收（含 burst 段）与 TCP_INFO/TCP_NOTSENT_LOWAT 缓解。

### R-18 TCP 慢启动双重污染：tcp_slow_start_after_idle 使停顿后 cwnd 重置，每场景冷连接又无 warmup 丢弃制度

- **视角**：SSE 流式计时　**严重度**：medium　**影响**：T1/T2/T3/U1/U2/N1　**闭环阶段**：阶段1
- **失真机理**：S2 刻意设计 think_pause 2–5s 与簇间停顿 300–800ms。Linux 服务端默认 tcp_slow_start_after_idle=1：空闲超 RTO 后 cwnd 坍缩，停顿后首个突发簇要重新慢启动，pause 后首批 ITL 系统性偏大并可能过 200ms stall 线——服务端 TCP 配置产物恰好集中出现在 S2 主场景的特征节奏上，使「Agent 流量额外压力」（S2−S1 对照）被放大。另一层：「每场景新建连接」意味着每个流式/上传阶段都跑在冷拥塞窗口上——S2 的 512KB 上行突发在慢启动阶段完成大半，U1 测的是 cwnd 爬坡而非链路容量；蜂窝下场景切换空隙足以让 RRC 回落，S1 作为首个场景永远承受最冷的无线状态，固定执行顺序系统性污染对照。参考项目「warmup 全丢弃」制度在本设计无对应物。
- **缓解措施**：VM 部署脚本固定 net.ipv4.tcp_slow_start_after_idle=0，sysctl 快照（连同拥塞控制算法名，建议固定 cubic/bbr）写入每次运行的服务端元数据；阶段 1 用 netem 零注入基线量化该参数开/关对 S2 T3 的影响并存 evidence/；每场景开头加固定 radio-warm 阶段（/echo ×5，丢弃），保留 dnsStart/connectStart/secureConnectEnd 分解字段使 U1 可复算「剔除慢启动」与「含慢启动」两口径；取证模式 S1/S2/S3 执行顺序在 3 遍间轮转（拉丁方）并记录实际顺序；上行逐块打戳必须落库；对照解读注明真实 LLM 服务端此参数状态属 claim boundary 外。
- **对抗验证结论**：风险中"tcp_slow_start_after_idle 污染 S2 停顿后 ITL/T3"这一半被算术推翻——簇内 100tok/s×120–300B 的应用限速流每 RTT 在途仅约 1–3KB，远低于 IW10≈14.6KB，cwnd 坍缩不会给亚 IW 发送增加任何额外 RTT，经 5.3.4 节奏剥离后不可能制造 200ms stall；但"每场景新建连接使 512KB/1MB 上传全程跑在慢启动爬坡上"这一半真实成立（512KB≈350 MSS 需约 5–6 个 RTT 爬坡，蜂窝 RTT 50–100ms 下测得 goodput 可比链路容量低一半，U1 优级 >20Mbps 门限实质变成 RTT×IW 联合测试，且真实 Agent 复用暖连接、冷连接口径超出 claim boundary），设计文档仅有部分缓解——§5"上行逐块打戳得到吞吐时间序列"使事后可复算剔除爬坡口径、每场景 clock_sync /echo×20（§3.2、KPI 5.3.2）事实上充当 RRC 预热削弱了"S1 最冷"顺序污染——但 U1 统计口径（KPI 5.1）未定义剔除慢启动、服务端 sysctl/拥塞算法快照未入元数据（设计§7 只记设备侧）、取证模式三遍无场景顺序轮转（KPI 5.3.6），故判成立但降为 medium 且仅影响 U1 及横比可比性，不影响 T 组主结论。

### R-19 pause 后首 token 混入 ITL 统计：C-DRX/RRC 唤醒税被计入 stall 率，且强依赖终端 5G 省电设置破坏横比

- **视角**：SSE 流式计时　**严重度**：medium　**影响**：T2/T3/T4/U2/AQS　**闭环阶段**：阶段1
- **失真机理**：S2 的簇间停顿 300–800ms 与 think_pause 2–5s 恰好横跨 C-DRX 长周期与 RRC inactivity 降级的时间尺度：静默后首个 token 的到达间隔天然包含「无线层唤醒税」（等 DRX on-duration 甚至 RRC 重建，多出几十到几百毫秒）。按当前口径这些间隔与稳态 ITL 混在一起：S2 的 stall 率被 pause 结构性推高（每次 pause 贡献一个候选 stall），T3 对 pause 设计参数敏感而非对网络敏感，S1 vs S2 对照混入结构项，削弱「S2−S1 = Agent 流量额外压力」论断的纯度。且该效应强依赖终端设置——各厂商「智能 5G/5G 省电」开关影响 DRX 请求，同一张网不同手机 T2/T3 可差一档，无法区分「运营商 DRX 配置激进」与「手机省电设置激进」，跨设备横比失效。注：唤醒税本身是真实且有价值的测量对象，问题只在口径混淆。
- **缓解措施**：客户端按 profile（seed 固定，pause 位置可精确预测）把「pause 后首 token 间隔」单列为新指标 resume_latency（按前置静默时长分桶 <100ms/300–800ms/>2s，分布+P95），从 T2/T3 的 ITL 样本集剔除；stall 率给出含/不含 resume 两口径；resume_latency 与 R1 的 DRX/RRC 状态对齐做归因——这反而是向运营商展示 C-DRX 参数影响 Agent 体验的独立证据；TestRun 元数据记录 5G 省电类设置（不可编程读取的写入测前人工 checklist）；同设备同 SIM 做省电开关 on/off A/B 标定实验，结论写入方法学附录。
- **对抗验证结论**：部分成立且未闭环：KPI 5.3.4 的逐序号"到达间隔−发出间隔"剥离已把 300–800ms/2–5s 的故意停顿本身从 T2/T3 口径中扣除（风险描述中"每次 pause 天然贡献一个 >200ms 候选 stall"这一机制被设计规避），但剥离后的残差仍完整保留 C-DRX 唤醒/RRC 恢复税——S2 每次 run 约 50+ 次簇间/思考停顿后的首 token 各携带几十至数百 ms 的设备省电设置依赖项，与稳态 ITL 样本混在同一分布进 T2/T3/T4/AQS，且设计文档 4.6 守卫只查 Android 省电模式、未记录厂商"智能 5G/DRX 类"设置，R 组 1Hz 打点也无法观测 DRX 态，故"pause 后首 token 单列 resume_latency + 记录 5G 省电设置元数据 + 同机 A/B 标定"的缓解仍然必要（降为 medium 是因为最大失真项已被 5.3.4 结构性削去）。

### R-20 SSE 响应头与首 event 同帧发出：T1 无法区分「网络到达」与「服务端 dwell」

- **视角**：SSE 流式计时　**严重度**：medium　**影响**：T1　**闭环阶段**：阶段0
- **失真机理**：Go handler 里 WriteHeader 后若立即写首 event 并 flush，HEADERS frame 与首个 DATA frame 可能同一 TLS record 落地；T1 定义中「减去服务端已知注入时延」要求知道服务端从收完请求到发出首 token 的真实 dwell，但当前 /stream 设计里首 event 之前没有任何服务端时戳锚点——Go 调度、TLS 首写、handler 启动开销全部悄悄计入 T1 的「网络分量」。对 T1「优」门限 <200ms 而言，几十毫秒的服务端 dwell 误差足以跨档。
- **缓解措施**：服务端在响应头写出后立即 flush 一个 SSE 注释帧「: prelude {srv_ts}\n\n」，再按 profile 节奏发首 token；客户端把 T1 拆为「请求发完→prelude 到达」（纯网络+握手残留）与「prelude→首 token」（服务端注入节奏，应≈profile 期望值）两段，后者偏离预期超阈值时标注服务端 dwell 异常而非记入网络。
- **对抗验证结论**：核心成立：/stream 首 event 前确无"请求到达"服务端锚点，T1 定义（KPI 5.1）只减"已知注入时延"，实际 dwell（handler 启动、TLS 首写、Go 调度）混入网络分量且无法用首 event 的 srv_ts 剥离（srv_ts 只给发出时刻、缺请求接收时刻）；现有闭环手段均不完整——5.3.4 节奏剥离只作用于 ITL 不作用于 T1，设计文档 §4.3/§6 的发送误差自检以 handler 启动为锚且用全流 P99>5ms 判失真，单个首 event 的几十毫秒离群完全撼不动数百样本的 P99，恰好放过 T1 这一"每流仅 1 样本"的指标；但风险陈述有两处夸大：HEADERS 与首 DATA 同 TLS record 对 T1 无影响（客户端打戳在 event 首字节而非响应头），且专用 Go 裸 VM 上常态 dwell 是亚毫秒到几毫秒级，几十毫秒属云调度尾部事件，故定 medium 而非 high；建议采纳 prelude 注释帧方案或在首 event 内附带 req_recv_ts。

### R-21 Cristian 对称路径假设在蜂窝上被系统性打破：TTFT 上下行拆分是方向恒定的偏置，且 ±RTT/2 不确定度无下游消费机制

- **视角**：时钟与归因　**严重度**：medium　**影响**：T1/U1/U2/N1　**闭环阶段**：阶段1
- **失真机理**：4 时间戳握手取最小 RTT 估 offset，假设去程=回程各占 RTT/2；但蜂窝结构性不对称：上行要经历 SR/BSR/授权等待，上行单向时延常比下行大 10–30ms 且随负载波动——这是方向恒定、次次可复现的系统偏差而非 ±RTT/2 的随机误差，反而因可复现显得可信。用自身依赖对称假设的尺子去测「上下行不对称」是循环论证。且蜂窝 RTT 50–100ms 时 ±25–50ms 的区间可横跨「上行是瓶颈」与「下行是瓶颈」两个相反结论，而 KpiCalculator→AqsScorer→ResultScreen 链没有任何一步会因不确定度过大而抑制或标灰数字——拆分值一旦渲染成结果页数字，取证报告就会当真值引用，向运营商主张「上行是瓶颈」时会被打回。
- **缓解措施**：所有依赖 offset 的派生量在数据模型定义为区间类型 {low, high, method}，不提供单点字段（按最坏不对称 0%~100% 分配 RTT 给出 [下界,上界]），schema 层杜绝点值引用；区间宽度 > 所在门限档位宽度 50% 时输出 indeterminate，UI 显示「不可判定」；明确白名单：T1 总量、T2/T3/T4（间隔差不依赖 offset）、U1 goodput 可出单点值，仅拆分类派生量受限；TTFT 拆分改三段法：把「服务端 dwell（收完→首 event flush，纯服务端时长、零 offset 依赖）」先剥离；结果 JSON 加 asymmetry_unknown=true 标志与 const 锁定的 claim_scope，claim scope 显式降级为实验性派生量、不进 AQS；阶段 1 用 tc netem 单向注入 50ms 时延做对抗实验，实测标定拆分可信度；对外报告禁止单独引用上/下行段点值，只允许引用双向和。
- **对抗验证结论**：风险对"TTFT 上下行拆分"这一派生量真实成立：设计文档 §4.2 明确用 Cristian offset 做"上/下行归因"，而蜂窝上行 SR/BSR/调度授权时延是方向恒定的系统偏差，用对称假设的时钟去为"上下行不对称"主张背书确属循环论证；KPI 文档 5.3.2 仅要求"标注 ±RTT/2 不确定度"、设计文档仅"随结果存档"，把系统性偏置错误刻画为对称随机误差，且 KpiCalculator→AqsScorer→ResultScreen 链无任何区间抑制/不可判定机制，取证报告确可引用拆分点值——故未闭环。但需修正风险陈述的夸大部分：affected_kpis 列出的 T1（首尾均为客户端单调时钟、不依赖 offset）、T2–T4（间隔差）、U1（goodput）、U2（往返减 200ms）、N1（RTT）按 5.1 定义全部零 offset 依赖，AQS 全部输入均不受污染，爆炸半径仅限于取证报告中的拆分归因叙事而非评分链，故定级 medium 而非 high；建议采纳的缓解为拆分量降级为区间型实验性派生量+不进报告点值引用+netem 单向注入对抗标定。

### R-22 时钟 offset 只在场景头标定一次：90s 场景内晶振/虚拟化时钟漂移使尾部拆分静默放大误差

- **视角**：时钟与归因　**严重度**：medium　**影响**：T1/U1/U2/N1/N2　**闭环阶段**：阶段1
- **失真机理**：clock_sync 只作为 phases[0] 执行一次，S2 长约 90s。手机与 VM 的相对频率偏差（普通晶振 ±20–50ppm，云 VM 虚拟化时钟可到百 ppm）在 90s 内积累 2–9ms——与「优」级 N2 抖动门限（<10ms）同量级，且单调递增不是随机噪声。场景尾部第二个 token_stream 的 TTFT 上下行拆分、上行逐块序列与服务端到达序列的对齐，用的还是 90s 前的 offset——误差在场景后段静默放大，且无任何字段记录这一点。
- **缓解措施**：profile 末尾追加第二个 clock_sync phase（尾部 20 样本），场景内所有依赖 offset 的计算按首尾两次 offset 线性插值（skew 校正），漂移率随结果存档；漂移率 >100ppm 或首尾 offset 差超出 2×(min-RTT差+漂移预算) 时打 offset_suspect 标；快测模式跨 S1/S2/S3 三个 offset 做一致性校验，互差异常即整个 run 的单向拆分降级为不可用。
- **对抗验证结论**：成立但范围被夸大：offset 漂移确实污染场景尾部依赖绝对 offset 的单向拆分（T1 上下行拆分、U 组逐块与服务端到达序列对齐），设计仅一次 clock_sync（profile phases[0]、设计文档 §4.2）且只存档 ±RTT/2 不确定度（KPI §5.3.2），无 skew 校正或漂移标记，故未闭环；但 N2/T2 抖动是逐 token「到达间隔−发出间隔」差分（§5.3.4），常量 offset 与 ppm 级 skew 在毫秒级间隔上贡献仅微秒量级，天然免疫，且蜂窝路径下已声明的 ±RTT/2（约 ±15–40ms）通常大于 90s 内 2–9ms 漂移，故定 medium 而非 high；建议采纳尾部第二次 clock_sync + 首尾线性插值的缓解。

### R-23 20 个 /echo 同步样本背靠背发送：RRC 状态迁移与同一拥塞周期整体污染 min-RTT，一次毒害 offset 与 N1/N2

- **视角**：时钟与归因　**严重度**：medium　**影响**：N1/N2/T1　**闭环阶段**：阶段1
- **失真机理**：×20 采样若在 1–2 秒内连发（实现上最自然的写法）：其一，蜂窝空闲态首包要经历 RRC idle→connected 建立（可达数百 ms），前几个样本被污染；其二，20 个样本落在同一调度/拥塞周期内高度相关，若此刻恰有瞬时拥塞，min 也不是无排队 RTT——offset 系统性偏大且无从发现。N1/N2 与 offset 用同一批样本，一次污染同时毒害网络基线分和所有单向拆分。
- **缓解措施**：采样前先发 2–3 个丢弃的预热请求把 RRC 顶到 connected；样本间加 100–300ms 随机间隔去相关；落 offset 质量指标（min 与 P10 差、变异系数），超阈值即 offset_low_confidence，fail-closed 抑制单向拆分输出（三态 Gate）；每样本 RTT 原始序列全量入 Room 供事后审计。
- **对抗验证结论**：成立但需修正一半：RRC 污染被部分天然规避——echo 走"同连接复用"（KPI 5.1 N1 行），TCP+TLS 建连本身把 RRC 顶到 connected 后才开始 20 次采样，数百 ms 的 idle→connected 时延落在建连而非 RTT 样本里（早期调度授权爬坡仍可能抬高前几样本）；但核心指控成立：两份文档均未规定样本间隔、预热丢弃或 offset 质量门限，20 样本背靠背落在同一拥塞周期时 min-RTT 与 P50/P95 高度相关且系统性偏大，N1/N2/offset 同批同污染。KPI 5.3.2 仅要求"标注 ±RTT/2 不确定度"、设计文档 §4.2 仅"误差随结果存档"——这是记录不确定度而非质量闸门，min 被抬高时 ±RTT/2 反而低估偏差且无 fail-closed 抑制单向拆分；echo 原始 RTT 序列也不在 §7 数据模型中（TokenEvent 全量但无 EchoSample），事后审计缺失。定 medium 而非 high：T1 总值不依赖 offset（纯客户端两时戳，offset 只影响上/下行拆分），N1+N2 合计仅占 AQS 20%，且每场景重新同步限制了单次污染的爆炸半径。建议采纳缓解项：2–3 个丢弃预热 + 100–300ms 随机间隔 + min−P10/变异系数质量指标 + 低置信时抑制单向拆分输出 + echo 样本全量入 Room。

### R-24 Go 时间戳序列化默认走墙钟 UnixNano：云 VM NTP 步进一次即伪造 >1s 卡顿并触发 T4 一票否决

- **视角**：时钟与归因　**严重度**：medium　**影响**：T2/T3/T4/AQS　**闭环阶段**：阶段0
- **失真机理**：KPI 文档只规定客户端禁用墙钟，服务端无对应条款。Go time.Now() 含单调分量，但把 srv_ts 序列化进 SSE event（转 UnixNano/毫秒）时单调分量被剥离，落到线上的就是墙钟。云 VM 的 chrony 步进（宿主机校时、热迁移后补偿）会让墙钟瞬间跳 ±几十 ms 到秒级：跳变点上「服务端发出间隔」出现巨大伪值，到达间隔−发出间隔产生反向伪尖峰，一个 >1s 的伪 ITL 直接把 T4 顶过 1% 触发 AQS 封顶 54——一次 NTP 校时毁掉整场取证。服务端 flush 自检若用单调钟内部比较，完全看不到这个问题。
- **缓解措施**：服务端 srv_ts 一律用进程启动锚点的单调差（time.Since(procStart)）序列化，墙钟仅在流开头发一次锚点映射；VM 的 chrony 禁 makestep（只允许 slew），chronyc tracking 输出定期快照进 /results 元数据；流内每 N 个 event 附带一次「单调-墙钟差」，客户端检测跳变即把跳变窗口样本标失真；阶段 0 联调时人工 date -s 制造一次步进做对抗验证。
- **对抗验证结论**：机制真实成立：KPI 5.3.1 只约束客户端单调钟，设计文档 4.3/6 未规定 srv_ts 时基，Go 自然实现序列化即墙钟；且现有对策（设计文档第 9 节"发送误差自监控 P99>5ms"）闭不了环——自检若用 Go 内部 time 运算走单调分量对步进全盲，即使用墙钟比较，单次步进只污染 1 个 event，在 ~1100 event 中根本推不动 P99>5ms 触发线，同理也顶不过 T4 的 1% 一票否决（风险描述"AQS 封顶 54"夸大，单次步进≈0.07% 占比）；真实伤害是：一个伪 >1s 剥离后间隔使 T4 从"优"（要求严格为 0）掉级、srv_ts 出现负向发出间隔污染 5.3.4 节奏剥离与阶段 0 对齐验收，且全程无告警——对取证工具属实质缺陷，建议采纳单调锚点序列化+chrony 禁 makestep 的缓解。

### R-25 flush 误差自检与被测对象共用同一 VM 时钟：kvmclock 冻结类失真自我豁免，发送空洞被 100% 冤枉给网络

- **视角**：时钟与归因　**严重度**：medium　**影响**：T2/T3/T4　**闭环阶段**：阶段1
- **失真机理**：「实际 flush 时刻 vs 期望时刻 P99>5ms 标失真」的两个读数来自同一 guest 时钟。vCPU steal 导致 goroutine 迟醒时自检能抓到；但 kvmclock 在热迁移/宿主机暂停期间整体冻结时，goroutine 停摆与时钟停摆同步发生——恢复后自检读数显示节奏完美，而线上实际出现了一段发送空洞。客户端把空洞测成大 ITL，节奏剥离时服务端却声称发出间隔正常，空洞被全额归因给「网络」。典型的自我参照失效。
- **缓解措施**：服务端跑独立哨兵 goroutine：每 10ms 自增计数并对照单调钟，检测「时间连续但调度空洞」与「调度连续但时间跳跃」两类异常，异常窗口随流标记；采集 /proc/stat 的 steal% 与当前 clocksource 随结果存档，steal 高峰期样本降级；客户端交叉校验：「到达间隔−发出间隔」出现服务端未标记的孤立大尖峰且同时刻 R 组无线层无异常时，自动打 server_clock_suspect 标供人工复核；选独享型实例并把实例规格写进 TestRun 元数据。
- **对抗验证结论**：flush自检、pacing时刻表与srv_ts共用同一guest单调钟，kvmclock随vCPU一起冻结（热迁移/宿主暂停）时自检必然读零误差且绝对时刻表无追赶突发、§4.4批化检测也不触发，发送空洞被5.3.4节奏剥离全额归因网络并污染T3/T4尾部证据；设计文档§9第2行给出的对策恰是该失明的自检本身加独享实例（不防迁移），未闭环——但发生率低（迁移事件稀少且单次测试仅4–12分钟），故定中危；另注意其建议的哨兵goroutine同样无法从guest内部检测完全冻结，真正有效的是客户端交叉标记与steal%/clocksource存档。

### R-26 快测模式单遍样本被当结论输出 AQS；S3/S2 profile 自带 U1 口径违约

- **视角**：统计与结果合同　**严重度**：medium　**影响**：T1/U1/AQS　**闭环阶段**：阶段1
- **失真机理**：快测模式各场景仅跑 1 遍即输出 0–100 的 AQS 头条分：T1 每场景只有 1 个样本（「取场景内中位数」是 1 个数的中位数），一次 RRC 建立慢或小区边缘瞬时就成为该设备/该网络的「分数」，且结果页对快测/取证两种模式无呈现区分，单样本快测截图流传出去就是「某运营商 AQS=xx」的结论。另有硬伤：U1 口径要求「每场景 ≥3 次上传取中位数」，而 S3 profile 只有 1MB×2、S2 只有 512KB×1（还不是 1MB 口径）——U1 在任何预置场景里都凑不齐样本，实现者只能私自放松口径。
- **缓解措施**：结果 JSON 顶层加 mode + evidential:bool 字段，快测 AQS 强制渲染「指示性（单遍）」水印且导出文件名带 quick 前缀；修正口径冲突：要么 S3 改 1MB×3、S2 上行突发按 512KB 单独命名（U1a）不与 1MB 口径混算，要么 U1 口径改「≥2 次，n 随结果存档」；取证模式明确聚合次序：先逐 run 算 KPI 与 AQS，再取 run 间中位数，禁止跨 run 拼出没有任何一次实测对应的「弗兰肯斯坦 AQS」。
- **对抗验证结论**：核实成立且无闭环：U1 口径（KPI 文档 5.1「每场景 ≥3 次上传取中位数」、默认 1MB）与预置场景硬冲突——S3 仅 1MB×2、S2 仅 512KB×1（设计文档 3.1，且 profile「发布即冻结」），任何单遍 run 都凑不齐 3 个合口径样本，而 U1 占 AQS 15%；快测模式单遍即出 AQS（KPI 5.3.6），T1 为单样本中位数，设计文档仅在 TestRun 元数据记录模式（§7），ResultScreen（§5）未要求任何快测/取证呈现区分或单遍水印；取证模式「3 遍取中位数」也未规定先逐 run 算 AQS 还是逐 KPI 跨 run 取中位数再合成。缓解仅为部分（§1 内部工具定位、阶段1验收含 5 次快测波动 ≤±5 分），均不闭环口径冲突与结果合同问题；定为 medium 而非 high 是因文档尚处待评审基线，属可低成本修正的规格不一致而非隐性物理失真。

### R-27 ITL 对数分桶直方图跨越 200ms/1s 门限：服务端复算与本地明细双写口径分叉，动摇取证公信力

- **视角**：统计与结果合同　**严重度**：medium　**影响**：T2/T3/T4　**闭环阶段**：阶段1
- **失真机理**：数据模型规定服务端只收「ITL 直方图（对数分桶）」，TokenEvent 全量仅存本地 Room。对数分桶的桶边界几乎必然跨越 200ms（T3 线）与 1s（T4 线）：一个 [158ms, 251ms) 的桶里既有 stall 也有非 stall，任何人从服务端 JSONL 复算 T3/T4/P95 都会得到与手机端不同的数字——取证场景下对方复核数据集时结论对不上。且分桶参数没写进版本化合同，换一版实现桶界一变，历史数据不可比。
- **缓解措施**：分桶方案写进版本化合同并强制门限值为桶边界：桶界集合 = 对数网格 ∪ {100, 200, 400, 1000ms}（T2/T3/T4 全部门限锚点），保证直方图复算的 stall 率与本地精确值一致；上报体同时携带手机端已算好的 KPI 数值 + 直方图 + 桶界版本号；评估上报预算——流式阶段全量 ITL 序列压缩后 <2KB 完全塞得进 200KB 限额，优先直接上报原始序列，直方图只作降级方案。
- **对抗验证结论**：设计文档§7仅写"ITL 直方图（对数分桶）"，桶界既未与 T2/T3/T4 门限（100/200/400/1000ms，KPI 文档 5.4 表）对齐也未纳入§3 的版本化 profile 合同，跨 200ms/1s 边界的桶使服务端 JSONL 复算 stall 率必然偏离手机端精确值——对以"取证"为定位的工具是真实口径分叉；判 medium 而非 high 的原因：上报体已含 ScenarioResult 的手机端 KPI 值与分级（权威数字在服务端可查），且本地 Room 全量 TokenEvent 可经 Exporter 导出供审计，直方图仅是佐证通道，但"佐证复算对不上权威值"与"桶界不versioned 致历史不可比"两点确实无任何现有条款闭环（5.3 全节与§7 均未规定桶界）。

### R-28 AQS 把「到单节点的路径质量」算成「网络体验分」，N1 与 T1 对同一段 RTT 双重计权，锚点插值还有未定义区

- **视角**：统计与结果合同　**严重度**：medium　**影响**：AQS/N1/N2/T1　**闭环阶段**：阶段1
- **失真机理**：AQS 的 N 组占 20%，N1 是到国内单一云 VM 的应用层 RTT；T1 的主要构成同样是这条路径的一个 RTT+首包调度。同一用户测深圳节点和北京节点，无线侧完全相同，AQS 却差一档——地理距离被 N1(10%)+T1(20%) 双重计入，AQS 名义是「Agent 网络体验分」，实际测的是「该设备到该 VM 的路径分」。风险表虽写了「只声明至该节点路径」，但 AQS 是对外头条数字，单一分数天然抹掉限定。另外锚点插值有未定义区：「优」档内上界锚点没定义，85→100 的插值斜率是实现者自由发挥，同一数据不同实现算出不同 AQS。
- **缓解措施**：aqs v0.1 profile 补全每档两端锚点（含 0 值→100 分的显式定义），插值函数写单测金样本；结果页与导出 JSON 强制 AQS 附带 scope: "to_node:<node_id>" 与节点地理位置，报告模板 AQS 旁固定展示三组子分（流式/上行/基线）防止单数字传播；v0.2 重标定时评估 N1 降权或改为「剔除传播时延的净抖动指标」，避免与 T1 双重计入距离；快测报告加「更换节点会改变本分数」固定脚注。
- **对抗验证结论**：核实成立：KPI 5.4 中 N1(10%)+N2(10%)+T1(20%) 均随到单节点的传播时延单调变化，约 30-40% 权重双重计入同一条路径的地理距离，换节点即换档而无线侧不变；且 5.4 只定义了 85/70/55 三个内部锚点，"优"档上界（何值得 100 分）与"差"档下界（何值得 0 分）两个开放区间的插值锚点完全未定义（T4 优档=0 还是点值非区间，U1 优档 >20Mbps 无上锚），同一数据不同实现可算出不同 AQS，与设计文档第 1 节"可重复性优先"直接冲突。设计文档 9 节风险表"结果只声明至该节点路径"仅是文字限定，未落到 AQS 输出合同（结果页/导出 JSON 无强制 scope 字段、无子分展示要求），双重计权与锚点未定义两点均无任何条款覆盖，故未闭环。定为 medium 而非 high：阶段 1 仅单节点单实现（AqsScorer），同节点内跨设备/跨运营商横比仍有效，失真主要在跨节点对比（阶段 3）与第三方复算时显现，且修复成本低（补锚点+金样本单测+scope 字段）。

### R-29 U2 的 P95 来自 8 个样本 = 事实上的最大值；T4 门限粒度低于样本分辨率成为高杠杆抖动放大器

- **视角**：统计与结果合同　**严重度**：medium　**影响**：U2/T4/T2/AQS　**闭环阶段**：阶段1
- **失真机理**：S2 工具循环仅 8 轮，U2 统计口径写「取 P95」——最近秩法 ceil(0.95×8)=8，8 样本的 P95 就是最大值：单次偶发调度毛刺直接决定这项 10% AQS 权重的 KPI，run-to-run 波动极大却以「P95」之名呈现稳健分位数的假象。同理 T4 门限 0.2%/1% 在 S1 的 599 个间隔上分辨率是 1/599≈0.17%：一个坏间隔就从「优」跳过「良」，一票否决线 >1% 只差 6 个间隔。
- **缓解措施**：结果合同为每个分位数 KPI 声明最小样本量与分位数方法（最近秩），n 不足时标 low_confidence 且不进 AQS 或降权；U2 改为报告中位数+最大值两个字段（n<20 时禁止填写 P95 字段），或把 S2 tool_loop 升到 20 轮（时长仅 +2.4s）；T4 改为「>1s 间隔绝对计数+占比」双呈现，否决条件写成计数域（≥N 个）而非百分比，消除分母敏感性。
- **对抗验证结论**：核实成立：KPI 文档 5.1 明确 U2「S2 场景每轮 1 样本，取 P95」而 S2 profile tool_loop rounds=8，最近秩 ceil(0.95×8)=8，P95 即最大值，单次调度毛刺直接决定这项 10% 权重 KPI；T4 在 S1（600 token→599 间隔）分辨率 1/599≈0.17%，且 >1% 一票否决线（AQS 封顶 54）仅需 6 个坏间隔，分母敏感性真实存在（细节小误：1 个坏间隔=0.17%<0.2% 落「良」而非跳过「良」，但不影响主论点）。现有条款未闭环：5.3.6 取证模式「3 遍取中位数」只对 run 级中位数做了缓冲且快测模式（单遍、输出 AQS）完全暴露；5.2「实验性门限待重标定」针对门限值而非样本量/分位数方法；设计文档第 7 节结果合同未声明分位数方法与最小 n，第 9 节风险表也未列此项。定为 medium 而非 high：不产生方向性错误（P95=max 偏保守），但直接威胁阶段 1 验收「连续 5 次快测 AQS 波动 ≤±5 分」及工具「可重复性优先」的立身原则，建议按提议在结果合同中声明分位数方法+最小样本量、U2 增样本或改报中位数+最大值、T4 双呈现计数与占比。

### R-30 Claim scope 泄漏：App 层测量被命名/表述成网络层与无线层结论，时间相关性被说成因果

- **视角**：统计与结果合同　**严重度**：medium　**影响**：T1/T2/T3/T4/R1/AQS　**闭环阶段**：阶段0
- **失真机理**：T1 直接命名为「TTFT（网络分量）」，但它是 OkHttp 回调线程测的应用层区间，仍含客户端 TLS 记录解析、OkHttp 事件分发、Kotlin GC、SSE 读取的用户态开销——命名本身就在做归因声明。「无线层打点用于把 stall/中断事件归因到切换」是把时间相关性直接说成因果（stall 与 PCI 变化同时发生也可能共同源于弱覆盖）。项目背景是「向运营商与标准组织展示证据」，一旦 AQS/stall 被表述成「某运营商 5G 网络导致 Agent 卡顿」，正是声明边界（禁止称 radio RTT/RAN 时延）明确防范的失真。
- **缓解措施**：结果 schema 每个 KPI 用 const 锁定 measurement_scope: "application_end_to_end"，T1 更名为 ttft_app_net_ms 或在定义里显式列出「包含但无法分离的客户端开销」；R 组字段统一命名为 covariate（协变量）而非 attribution；报告生成器维护禁用词表（RAN 时延、空口丢包、基站导致等），出现即 lint 失败；「切换归因」降级为「时间重合事件对」并要求最小重合窗口定义。
- **对抗验证结论**：KPI 文档 5.1 确实把 T1 命名为「TTFT（网络分量）」（仅剔除服务端注入时延，未声明客户端 TLS 解析/OkHttp 分发/GC 等无法分离的用户态开销），5.3.5 原文直接写「用于把 stall/中断事件归因到切换」，属时间相关性表述为因果；现有条款只有部分缓解（5.3.2 要求单向时延标注 ±RTT/2 不确定度、5.1 称 R 组为「协变量…不设门限」、设计文档 §9 的「只声明至该节点路径」），均不覆盖 App 层 vs 网络层的 claim scope 锁定与禁用词纪律——参考文档（参考_ChatGPT侧ANEB §63）自己也承认本仓库尚未落实该边界并建议补齐；判 medium 而非 high 是因为它不污染原始测量值，发布前通过更名（如 ttft_app_net_ms）、schema const 锁 measurement_scope、把「归因到切换」降级为「时间重合事件对」即可闭环，但鉴于项目目标是向运营商/标准组织出示证据，阶段 0 就应修正命名以免 v0.1 数据带错误标签沉淀。

### R-31 CGNAT 出口漂移：同一 TestRun 内不同场景走不同 NAT 路径，RTT 基线与 offset 互不可比，NAT 回收断流被记成网络卡顿

- **视角**：Android 平台与环境　**严重度**：low　**影响**：N1/N2/T1/T4/U2　**闭环阶段**：阶段1
- **失真机理**：国内蜂窝普遍 CGNAT。「每场景新建连接」+「每场景前 /echo ×20 估 offset」下，新建五元组可能被分配到不同 CGNAT 板卡/出口 IP，同一 run 内 S1 与 S2 的 RTT 基线和时钟 offset 各自成立但互不可比；取证模式 12 分钟内出口漂移让「S2 相对 S1 的额外压力」对照混入 NAT 路径差异。MVP 阶段（C3 放阶段二）对「流中途 NAT 映射被回收导致 RST」没有检测手段，会被记成 T4 严重卡顿或场景失败而非连接性事件。
- **缓解措施**：服务端每个端点响应都回显 observed source IP:port（/echo、/stream 首 event、/upload 响应各带一次），客户端逐场景存档；同 run 内出口 IP 变化即打 nat_path_shift 标并禁止跨场景对照结论；流式阶段异常断开时区分 FIN/RST/read timeout 三种终止方式记录，为阶段二 C3 归因预留证据字段。
- **对抗验证结论**：风险核心成立但被明显夸大：offset 子论断不成立（时钟偏移是设备-服务器钟差、与 NAT 路径无关，且设计为每场景独立同步并按 5.3.2 存档 ±RTT/2 误差，不做跨场景 offset 运算），且 H2 下单场景内 echo/stream/upload 共用一条连接、场景内各 KPI 自洽，场景活跃期最长静默仅 2–5s 远低于 CGNAT 空闲超时、流中被回收概率很低；真正未闭环的残留缺口有二——(a) 跨场景新建五元组的出口路径无任何观测手段（服务端不回显 observed source IP:port），5.3.7 的 S2-vs-S1 对照在取证模式 12 分钟内混入 NAT 路径差异时既不可检测也不可标记，(b) MVP 对流式阶段异常终止（RST/静默丢弃后 30s read timeout/FIN）无终止方式分类字段，静默回收会以 read timeout 形态被记成 T4 长间隔或未定义的"场景失败"（C 组含 C1/C3 整体推迟阶段二，设计 §8/§9 风险表均无 NAT 条目），建议采纳其低成本缓解（回显出口 IP:port + nat_path_shift 标记 + 终止方式三分类字段）。

### R-32 /echo 的 t1/t2 取自 Go handler 层：收/发方向隐藏栈内延迟不对称地污染 offset

- **视角**：时钟与归因　**严重度**：low　**影响**：N1/T1　**闭环阶段**：阶段1
- **失真机理**：4 时间戳握手要求 t1=服务端收到、t2=服务端发出，但 handler 能打的最早戳已在 TLS 解密、HTTP/2 帧分发、goroutine 调度排队之后；t2 打在 handler 返回前，响应还要过序列化与内核发送。t2−t1 低估驻留时间只是让 N1 略偏大；真正的问题是收方向隐藏延迟（解密+调度）与发方向隐藏延迟（序列化+发送）不相等且随负载浮动，这个不对称直接平移进 offset 估计，成为所有单向拆分的又一层系统偏差，且与路径不对称叠加、无法相互区分。
- **缓解措施**：/echo handler 做到极薄：固定长度二进制 body、预分配缓冲、零日志零反射，把栈内驻留压到百微秒级使不对称可忽略；t2−t1 随每个样本返回并入库，监控其 P99——驻留超过 1ms 即触发告警；阶段 1 做标定实验：同机用 SO_TIMESTAMPING/tcpdump 内核时间戳对照 handler 级 t1/t2，量化隐藏延迟的均值与不对称并写进方法学文档供 offset 误差预算引用。
- **对抗验证结论**：机制真实：Go handler 只能在 TLS 解密/H2 分发/调度之后打 t1、在序列化/内核发送之前打 t2，收发向隐藏延迟不对称确实平移进 offset；但该不对称在数学上被测得 RTT 完全包含，故被 5.3.2 强制存档的 ±RTT/2 误差条（蜂窝下即 ±10–50ms）先验覆盖，且取最小 RTT 样本天然滤掉随负载浮动的调度排队分量——专用 VM、<100B body 下残余固定不对称约百微秒级，比已声明不确定度低两个数量级，不会产生逃出误差预算的额外偏差；风险提出的薄 handler、/echo 驻留 t2−t1 监控与 SO_TIMESTAMPING 标定（设计目前仅对 /stream 做发送误差自监控）是可收紧误差条的加固项，而非闭环缺口。

### R-33【实测发现】运营商 SNI-keyed TLS RST 注入：电信 NR-SA 对特定 SNI 主机名握手中途双向 RST，阻断经 sslip.io 主机名的蜂窝取证

- **视角**：真机实测（非 4 视角枚举，2026-07-13 真机首测战役现场发现）　**严重度**：high　**影响**：REACH（新候选指标）/ T·U·N·AQS 蜂窝主通道前置门　**闭环阶段**：实测发现（缓解见 D-22）
- **机理**：中国电信 5G SA（NR-SA、n78）路径上存在按 **SNI 主机名内容**触发的选择性 TLS 干预：当 ClientHello 携带特定主机名（`*.sslip.io`、`*.nip.io` 等 wildcard-DNS 主机名）时，中间盒在握手中途注入双向 RST 使连接复位；同一主机名在 WiFi/固网侧完整放行；改用 **bare-IP**（`https://120.79.148.0:8443`，ClientHello 无 SNI 触发词）时 **TLS 握手可完整完成**（仅因证书缺 IP-SAN 报 SSLPeerUnverifiedException，属证书校验而非连接被杀）。故触发键是 SNI 内容、非端口（8443 本身在蜂窝上可用）、非目的 IP（ICMP/TCP 到同一主机正常）。真实生产域名（`api.moonshot.cn`）SNI 亦放行——干预面是 wildcard-DNS 类主机名而非全量 SNI。
- **真机证据**：同一设备（HUAWEI ELS-AN00 / EMUI 14.2 / SDK31）分钟级 A/B：(1) WiFi + `120-79-148-0.sslip.io:8443` → RUN_END 完成、REPORT http=200（run 019f59ad）；(2) 蜂窝 + 同主机名（sslip.io 与 nip.io 均） → 握手期间 Connection reset；(3) 蜂窝 + bare-IP `120.79.148.0:8443` → TLS 完成、仅证书不匹配 IP；(4) ICMP 基线 ping 120.79.148.0 avg 69ms、host/IP 层正常。证据文件 evidence/phase3/realdevice_first_campaign_20260713.log（step3 HEADLINE FINDING）。
- **与 P3-C11 的关系**：二者是**同类中间盒 TLS 干预的两种不同触发键**——P3-C11（evidence/phase3/STATUS.json / tls_cutover_20260713.log）是 PC↔E-01 路径上**按 TLS 栈指纹**（大 ClientHello：padding/GREASE/PQ key share，Windows schannel 10/10 被 RST、Go/OpenSSL 全通）的选择性 RST；R-33 是蜂窝路径上**按 SNI 主机名内容**的选择性 RST。一按协议栈指纹、一按握手内容，均表现为握手中途双向 RST，且失败时 App 行为均符合设计（INVALID/TRUNCATED + KPI_MISSING，评分语义未破坏）。两者共同支持"按{握手指纹, SNI, 协议栈}分组的握手成功率"作为独立探针 KPI 候选（REACH，见 KPI 文档 5.5）。
- **对测量的影响与缓解**：这是 ANEB 的**测量对象**（可量化的连接层中间盒干预维度）而非工具缺陷——蜂窝下经 sslip.io 主机名的 E-01 取证/AB（TCP vs QUIC）/连续性实验被此中间盒**整体阻断**（握手失败即无 T/U/N 数据、AQS 不可计算），需双通道隔离而非当作失败率计入。缓解（D-22）：① bare-IP + IP-SAN 自签证书（OkHttp 主测量不需 known-root）作为蜂窝主通道绕过 SNI-RST 采集真实 KPI；② 保留带 SNI 通道做 {SNI 主机名, bare-IP, 协议栈} 分组的握手成功率对比（REACH 候选指标）；③ Cronet QUIC 蜂窝受 known-root（D-21）+ SNI 双重约束，单独观测。**研究正当性边界**：本项目为自有服务器 + 自有设备 + 自有 SIM 的授权网络性能测量，SNI-RST 作为可量化测量维度纳入（带 SNI vs bare-IP 连接成功率），bare-IP 通道用于采集真实蜂窝 KPI，目的非规避审查。

## 已驳回项（对抗验证判定对本设计不成立）

| 风险 | 驳回理由 |
|---|---|
| T1 计时起点在 GET /stream 上未定义：requestBodyEnd 不触发，连接复用暖机使同场景/跨场景 T1 不可比 | 核心断言前提不符：T1 起点是"请求最后一字节发出"的字节级定义，对 GET 唯一映射到 requestHeadersEnd（不存在两可口径），且该起点在时间上晚于连接建立，TLS/cwnd/H2 SETTINGS 暖机被定义天然排除；加之每场景首 phase 的 clock_sync ×20 已把连接暖透，同场景首末 token_stream 与跨场景 T1 的连接状态实为均匀——仅剩"在 schema 中显式写明 GET 起点"一条文档润色建议，不构成真实测量失真。 |
| HTTP/2 流控窗口依赖客户端消费速度：读线程慢半拍即制造伪 stall 并误诊为中间盒缓冲 | 前提不符：OkHttp H2 初始窗口为 16MiB 而本设计 token 流单阶段总量 <1MB，且连接级 WINDOW_UPDATE 由 OkHttp 专用读帧线程回送、不依赖应用 SSE 线程消费；S3 的上传与流式为顺序 phase 而非同连接并发，流控耗尽制造伪 stall 的链条无法成立——残余的读线程 GC 批化属另一风险且已被设计文档 4.4/KPI 5.3.3 批化自检保守判无效。 |
| seed 固定随机流的两端实现不一致：Go 与 Kotlin 生成的序列必然不同，校验防线失效或 RNG 差异被记成网络抖动 | 该风险的核心失真路径（客户端用自生成的期望时刻做节奏剥离、把 RNG 差异记成网络抖动）与本设计明确矛盾：5.3.4 与设计文档 §4.3 规定网络贡献只能由每 event 内嵌的 srv_ts 逐序号对齐差计算，随机流仅由 Go 服务端生成一次并逐 event 下发 {seq, srv_ts, payload}，客户端"按 profile 校验预期"不需要也无处使用 Kotlin 重放随机序列（数据模型 TokenEvent 记录的是实收 payload_bytes），且服务端还有 flush 时刻 vs profile 期望时刻的自监控（P99>5ms 标失真）兜底；残余的小口子——"客户端内置版 vs 服务端版不一致仅告警不判 invalid"（§2）与 Go math/rand 跨 Go 版本序列稳定性——属实现纪律问题而非该风险声称的两端 RNG 必然失配，建议实现时把版本不一致升级为 run 级 invalid 并为生成器加金样本 CI，但不构成对 T1–T4 的成立性威胁。 |
